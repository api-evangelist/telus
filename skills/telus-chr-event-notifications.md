# Consume CHR event notifications

The Enterprise API Event Notification Service (ENS) is the only push surface anywhere in the TELUS
estate. It is a webhook mechanism: "allowing an API Consumer to receive notifications whenever one or
more specific events occur in your account."

## 1. Create the subscription

Subscriptions are created **in the CHR product, not through the API**:
**Settings > Enterprise API** > edit an API Consumer > **Subscriptions** tab > new subscription.
Supply a name, your endpoint **URL**, a **secret**, and select the topics you want. You can create
several subscriptions against one API Consumer.

## 2. Subscribe to the right topics

Appointments: `appointment.created`, `appointment.updated`, `appointment.canceled`,
`appointment.deactivated`

Patients: `patient_demographics.created`, `patient_demographics.updated`,
`patient_demographics.archived`, `patient.merged`

Encounters: `encounter.created`, `encounter.signed`, `encounter.unlocked`, `encounter.deleted`

Referrals: `referral.incoming.created`, `referral.incoming.updated`, `referral.internal.created`,
`referral.internal.updated`, `referral.outgoing.created`, `referral.outgoing.updated`

Questionnaires: `qnaire.completed`

Tasks: `task.created`, `task.updated` (added in version 26.02)

Do not invent a topic name — this is the complete published set. The full catalogue with the
delivery contract lives in `asyncapi/telus-chr-event-notifications.yml`.

## 3. Verify every notification

The CHR signs each notification with the secret you supplied and puts the resulting signature in a
request header. Verify it before doing anything with the payload. TELUS does not publish the header
name, so read it from a live delivery in your sandbox domain and pin it in configuration; treat an
unsigned or mis-signed request as hostile.

## 4. Treat the payload as a pointer, not as data

The payload is JSON and carries **only identifiers**: the common fields `topic`, `subscriptionId`,
`accountDomain` and `isImporting`, plus event-specific ids such as `appointmentId`, `patientId` and
`providerId`.

> "The notification payload contains only IDs and other fields, no personal information or personal
> health information."

That is deliberate — it is a claim-check pattern. Nothing clinical crosses the webhook. Hydrate the
record over GraphQL with the ids you were given:

```graphql
query Hydrate($id: ID) {
  appointment(id: $id) {
    id startAt untilAt
    patient { id firstName lastName }
    provider { id }
    location { id }
    service { id }
  }
}
```

Use `patient(id:)` for patient events, `task(id:)` for task events, `referralRecord(id:)` for
referral events. Each hydration call needs a fresh RS512 JWT (see
`skills/telus-chr-book-appointment.md`).

## 5. Handle retries and ordering

- On failure ENS retries **5 times with a backoff of 5, 10, 20, 60 and 120 minutes**. Your endpoint
  must therefore tolerate the same event arriving up to six times — key your processing on the
  event's resource id plus topic.
- Acknowledge fast: return a success status as soon as you have persisted the raw event, and hydrate
  asynchronously. A slow endpoint burns retry attempts.
- **No ordering guarantee and no deduplication contract are published.** Do not assume
  `appointment.created` arrives before `appointment.updated`; re-read the current state from
  GraphQL rather than replaying deltas.
- `isImporting` flags events generated by a bulk import rather than by user activity — use it to
  suppress downstream notifications during a migration.

## 6. Reconcile

Because there is no ordering or delivery guarantee, run a periodic reconciliation sweep with
`appointments(from:, to:, orderBy:, first:, after:)` and `patients(..., first:, after:)`, paging
through the Relay connections (default 50, max 100 per page). Every API action, including your
reconciliation reads, is audit-logged and retained for 90 days.
